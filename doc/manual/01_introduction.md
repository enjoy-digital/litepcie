# Introduction {#introduction}

This chapter says what LitePCIe is, why it exists, what it does and what it does not do. It ends
with the layout of the repository and a map of the manual. Every reader should start here.

## What the project is {#intro-what}

LitePCIe adds PCI Express to an FPGA design. It moves data between the FPGA and the memory of a
host computer, maps FPGA registers into the address space of the host, and sends interrupts to
the host. A Linux driver and command line tools are part of the project.

The project has four parts, shown in the figure below. The PHY connects to the PCI Express link;
the core turns the link traffic into requests and completions; the frontends give user logic
simple interfaces: DMA streams, memory-mapped buses and interrupt lines. The driver runs on the
host.

![LitePCIe at a glance. The PHY, hard IP or soft, carries the link; the core builds and parses
the packets and routes them; the frontends give user logic DMA streams, memory-mapped buses and
interrupts.](intro_overview.svg)

The gateware is written in Python with Migen and LiteX, and generates Verilog for the FPGA tools.
It can be used as a LiteX library in a LiteX SoC, or as a standalone Verilog core generated by
`litepcie_gen` from a YAML configuration (see [Integration](#integration)).

## Why LitePCIe {#intro-why}

Each FPGA vendor provides a PCI Express hard IP, but each one has its own interfaces, its own
packet formats and its own DMA engines. A design written for one vendor must be rewritten for the
next. LitePCIe puts one core on top of every hard IP, as the figure below shows.

![One core, many PHYs. The same core, frontends and Linux driver run on the hard IPs of four
FPGA vendors, or on the FPGA transceivers through the soft PHY.](intro_phys.svg)

The same DMA, the same registers and the same driver then work on every supported FPGA. Moving a
design from a Kintex-7 to a Kintex UltraScale+ changes the PHY and its parameters, not the user
logic or the host software.

The core is small and configurable. Data widths from 64 to 512 bits, the number of DMA channels,
the DMA plug-ins and the interrupt type are parameters, so a design pays only for what it uses.
Every layer is open and can be simulated, observed and changed.

The soft PHY goes further: it implements the physical and data link layers in the FPGA fabric, on
the transceivers, with no vendor IP. It is in development; [Soft PHY](#soft-phy) gives its status.

## Features at a glance {#intro-features}

| Area | Features |
|--------------------|------------------------------------------------------------------------|
| PHYs | Hard IPs of Xilinx 7-Series, UltraScale and UltraScale+, Intel Cyclone V and Stratix V, Gowin GW5A, Lattice CertusPro-NX; soft PHY on Xilinx GTP, GTX and GTY transceivers |
| Roles | Endpoint on every PHY; root port on Xilinx 7-Series, UltraScale and UltraScale+ |
| Core | TLP packetizer and depacketizer from 64 to 512 bits, crossbar, request tags and completion reordering, clock domain crossing |
| DMA | Scatter-gather Writer and Reader per channel, descriptor tables, loopback, PPS synchronizer, run-time buffering, monitor, status written to host memory |
| Memory-mapped | Wishbone master on BAR0, Wishbone and AXI slaves to host memory |
| Interrupts | MSI, multi-vector MSI, MSI-X |
| Time | Precision Time Measurement requester on Xilinx 7-Series and UltraScale+ |
| Software | Linux driver with DMA buffers and memory mapping, user library, `litepcie_util` and `litepcie_test` tools |
| Integration | LiteX library, or standalone Verilog core with AXI interfaces from `litepcie_gen` |
| Verification | Python host model, unit tests, Verilator simulations of the soft PHY up to the DMA |

## Supported FPGAs {#intro-fpgas}

The table below lists the PHYs, their highest rate and width, and their state.
[Supported FPGAs and boards](#boards) gives the boards and [Hard-IP PHYs](#hard-phys) the
details of each family.

| FPGA family | PHY | Highest rate | Lanes | State |
|----------------------|-------------------------|-------------|--------------|---------------------|
| Xilinx 7-Series | `S7PCIEPHY` | Gen2 | x1 to x8 | Validated on hardware |
| Xilinx UltraScale | `USPCIEPHY` | Gen3 | x1 to x8 | Validated on hardware |
| Xilinx UltraScale+ | `USPPCIEPHY` | Gen4 | x1 to x16 | Validated on hardware |
| Intel Cyclone V | `C5PCIEPHY` | Gen2 | x1, x2, x4 | Validated on hardware |
| Intel Stratix V | `SVPCIEPHY` | Gen2 | x1, x4, x8 | Validated on hardware |
| Gowin GW5A | `GW5APCIEPHY` | Gen2 | x1, x4 | Validated on hardware |
| Lattice CertusPro-NX | `LFCPNXPCIEPHY` | Gen3 | x4 | Validated on hardware |
| Xilinx GTP, GTX, GTY | `SoftPCIEPHY` | Gen3 | x1 to x8 | In development |

For the Xilinx and Stratix V PHYs, the rate and the lanes are the values the wrapper accepts. The
Cyclone V, GW5A and CertusPro-NX wrappers do not set the rate, the vendor IP configuration does:
the Cyclone V rate is the one the repository README gives, and the GW5A and CertusPro-NX rates
come from the device ID names of the driver (Gen2 x4 and Gen3 x4).

The soft PHY runs Gen1 and Gen2 links with a host, up to x8 on Kintex-7 GTX and x1 on Kintex
UltraScale+ GTY, and Gen3 links at x1, x4 and x8 on the GTY. [Soft PHY](#soft-phy) details each
state.

## Status {#intro-status}

Every hard-IP PHY is validated on hardware, with a Linux host. The repository records DMA
throughputs for some configurations, in Gb/s as `litepcie_util dma_test` prints them;
[Performance and resources](#performance) collects them.

The project is used in products. The LiteX-M2SDR, an M.2 software defined radio board on a
Xilinx Artix-7, uses LitePCIe for its PCI Express Gen2 x4 link, its DMA and its driver.

![The LiteX-M2SDR, an M.2 board whose PCI Express interface is built on
LitePCIe.](m2sdr_board.png)

## What it is not {#intro-limits}

LitePCIe is a single-function device or a root port. It does not implement the optional parts of
PCI Express that most FPGA designs do not need:

- Legacy INTx interrupts are not used: the device signals with MSI or MSI-X.
- Hot plug is not supported: the FPGA must be configured before the host enumerates the bus, or
  the bus must be rescanned.
- Multi-function devices, SR-IOV and virtual channels are not supported.
- Advanced Error Reporting and Address Translation Services are not implemented by the core.
- The core does not drive link power management; the soft PHY does not implement ASPM, L0s or
  L1.

The PHYs have their own limits, such as interrupt types or speeds per family. [Hard-IP
PHYs](#hard-phys) and [Soft PHY](#soft-phy) list them.

## Repository layout {#intro-layout}

| Path | Content |
|---------------------------|------------------------------------------------------------------|
| `litepcie/phy/` | Hard-IP PHY wrappers and their common datapath |
| `litepcie/phy/soft/` | The soft PHY: transceivers, physical, data link and transaction layers |
| `litepcie/tlp/` | TLP packetizer, depacketizer and controller |
| `litepcie/core/` | Endpoint, root port, crossbar, MSI and MSI-X |
| `litepcie/frontend/` | DMA, Wishbone and AXI bridges, PTM |
| `litepcie/software/` | Linux driver, user library and tools |
| `litepcie/gen.py` | The standalone generator `litepcie_gen` |
| `bench/` | Board targets of the hard-IP PHYs; `bench/soft/`: soft PHY targets and simulations |
| `examples/` | Configuration files of the generator |
| `test/` | Unit and simulation tests (pytest) and the host model |
| `doc/` | This manual (`doc/manual/`), its figures (`doc/diagrams/`), photos and developer notes |
